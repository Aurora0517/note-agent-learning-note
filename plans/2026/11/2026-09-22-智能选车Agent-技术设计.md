## 1. 架构总览

```
Web Chat 单页（SSE 流式）             极简评审页（M4，可并入 API）
        │ SSE                            │ REST
        └────────────► FastAPI ◄─────────┘
                        │
                  LangGraph 编排（双子图 + checkpoint 持久化）
                  ├── 子图1：选型对话（澄清 interrupt → 判定 → 报价/需求单）
                  └── 子图2：配置单组装（基准检索 → 差异匹配 → 评审 interrupt）
                        │
        ┌───────────────┼────────────┐
   工具层（函数调用 +      RAG 检索     LLM（OpenAI 兼容，
   vehicle-mcp Server）  Chroma + BGE  DeepSeek / Qwen 可配）
        │
   SQLite（M1-M2，业务数据 + checkpoint）→ PostgreSQL（M4 部署迁移）
                                        Langfuse Cloud（trace + 成本）

可选扩展（主线完成后）：Android 客户端（Kotlin + Compose）、Next.js 完整管理端
```

设计原则：
1. **LLM 只做三件事**：理解与槽位抽取、候选生成与解释、话术排版；金额、判定、可行性校验全部由规则/数据层负责
2. **环节间传结构化单据**（需求单/配置单），不传聊天原文；单据 schema 用 Pydantic 强校验
3. **所有长等待用 interrupt + checkpoint**：用户确认、管理端评审都是挂起点，不轮询不阻塞
4. **能力与端分离**：砍端不砍能力——编排、grounding、评测、HITL 全保留；Android/完整管理端为可选扩展

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| Agent 编排 | LangGraph（锁定版本） | 双子图 + interrupt + PostgresSaver |
| 服务端 | Python 3.11+ / FastAPI / uvicorn | SSE 用 `sse-starlette` |
| LLM 接入 | OpenAI 兼容协议 | `LLM_BASE_URL` 可切 DeepSeek / Qwen / GLM |
| 结构化输出 | Pydantic v2 + `with_structured_output` | 失败重试 + 温度 0 |
| 数据库 | SQLite（M1-M2）→ PostgreSQL 16（M4 部署迁移） | 迁移触发：多 worker 部署/并发写；SQLAlchemy 2.0 全程，Alembic 仅迁移期 |
| 向量库 | Chroma（起步） | 字段设计兼容迁移 pgvector |
| Embedding | BGE-M3（sentence-transformers 本地） | `EMBEDDING_MODE=api` 可切 SiliconFlow 兜底 |
| MCP | `mcp` Python SDK | vehicle-mcp 独立进程 |
| 观测 | Langfuse Cloud（自托管为可选升级） | 每次 graph run 一条 trace |
| 用户端 | 单页 Web Chat（原生 HTML/JS 起步） | SSE 流式；Android（Kotlin + Compose + OkHttp SSE）为可选扩展 |
| 评审端 | M4 主线：FastAPI + Jinja2 单页（列表/详情/通过/驳回） | Next.js 14 完整版为可选扩展 |
| 部署 | VPS + Docker Compose（M4） | api（含评审页）/ vehicle-mcp / postgres / chroma |

## 3. LangGraph 设计

落地节奏（v1.1）：M1 先手写 function-calling 循环（while + 工具分发，约百行）跑通端到端，完整暴露"模型决定调工具 → 结果回填 → 继续推理"的机制；M2 迁移 LangGraph 单图（动机：跨轮槽位状态与 interrupt 管理复杂化）；双子图为目标架构，子图2 在 M3 随评审恢复流落地。

### 3.1 共享 State

```python
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    slots: dict                # 已收集槽位：budget/use/passengers/energy/charging/must_have
    missing_slots: list[str]
    availability: str | None   # on_sale | discontinued | uncovered
    candidates: list[dict]     # 推荐候选（带评分）
    quote: dict | None         # 报价单（规则引擎产出）
    order: dict | None
    requirement_sheet: dict | None   # 定制需求单（结构化 + citations）
    config_sheet: dict | None        # 配置单初稿（基准 + 差异项 + citations）
    review_status: str | None        # pending | approved | rejected
```

### 3.2 子图1：选型对话

```
route_intent → extract_slots ─┬─ 缺槽位 → ask_clarify（interrupt：追问卡片）─┐
                              │                    （用户回复后 resume）◄──┘
                              └─ 槽位齐 → confirm_slots（interrupt：卡片确认）
                                      → check_availability
   ├─ on_sale → recommend → pick_and_quote → confirm_order（interrupt）→ create_order → END
   └─ discontinued/uncovered → build_requirement_sheet → enqueue_review → END
```

- `ask_clarify` / `confirm_order`：`interrupt()` 挂起，前端渲染对应卡片，`Command(resume=...)` 恢复
- `enqueue_review`：落库 `requirement_sheets(status=pending)`，通过 Langfuse 事件通知管理端
- 管理端评审动作：REST API 写库 + 触发子图2（新 thread）

### 3.3 子图2：配置单组装（管理端"通过"后触发）

```
fetch_requirement → search_base_model → diff_match → assemble_sheet → wait_review（interrupt）→ finalize
```

- `search_base_model`：结构化过滤（能源/吨位/马力段）+ 向量语义检索，取 Top1 为基准，Top2~3 备选
- `diff_match`：对需求与基准的差异项，先按 `parts.compatible` 规则过滤出可行件，LLM 只负责从可行集里选择并写理由
- `assemble_sheet`：模板组装，每行强制带 `citations[]`，无引用则该行退回 `diff_match`
- `wait_review`：管理端改单/通过/驳回，`Command(resume=review_result)` 恢复；驳回回到 `diff_match`

### 3.4 Checkpoint 与线程

- `thread_id`：子图1 = 会话 ID；子图2 = `sheet-{id}`
- checkpointer 持久化：M1-M2 用 SqliteSaver，M4 部署时迁 PostgresSaver；重进会话 = 同 thread_id 继续，遇到 interrupt 重新下发卡片
- 事件边界预留：两个子图本设计同进程，但子图2 只通过"需求单落库"事件触发，未来可直接拆独立服务

## 4. API 设计

### 4.1 聊天（SSE）

`POST /api/chat`　body: `{ "thread_id": str|null, "message": str }`

SSE 事件流：

| event | payload | 说明 |
|---|---|---|
| `token` | `{delta}` | LLM 文本增量 |
| `tool` | `{name, args_summary}` | 工具调用可视化 |
| `card` | `{type, payload}` | slot_confirm / candidates / quote / order / requirement_sheet / config_sheet |
| `interrupt` | `{type, payload}` | clarify / confirm / review，前端渲染操作按钮 |
| `done` | `{thread_id}` | 本轮结束 |

`POST /api/threads/{thread_id}/resume`　body: `{ "command": {...} }`　用于恢复 interrupt

### 4.2 其他

- `POST /api/admin/requirement-sheets/{id}/review`　`{action: approve|reject, edits?}` → approve 触发子图2
- `POST /api/admin/config-sheets/{id}/review`　`{action: approve|reject, edits?}` → resume 子图2
- `GET /api/vehicles` `GET /api/evals/summary` `GET /api/costs/summary`
- 鉴权：个人版静态 token；请求头预留 `X-Tenant-Id`（数据隔离设计预留）

## 5. 工具层

| 工具 | 职责 | 类型 |
|---|---|---|
| `search_vehicles` | 结构化+语义筛选车型 | 函数（M3 起 vehicle-mcp 同时暴露） |
| `get_vehicle` | 车型详情/配置 | 函数 / MCP |
| `check_availability` | 在售/停售/未覆盖判定 | 函数 / MCP |
| `compare_vehicles` | 2~4 款对比数据 | 函数 |
| `calc_quote` | 报价（规则：指导价-优惠-税） | 函数，禁止 LLM 参与 |
| `calc_financing` | 等额本息月供（纯公式） | 函数，pytest 断言零容错 |
| `search_knowledge_base` | RAG 检索（带 citation） | 函数 |
| `create_requirement_sheet` | 需求单落库 | 函数 |
| `find_base_model` | 基准车型检索 | 子图2 节点逻辑 |
| `suggest_part_alternatives` | 差异件可行集过滤 | 子图2 节点逻辑（规则） |

vehicle-mcp：`mcp` SDK 实现，暴露 `search_vehicles / get_vehicle / check_availability` 三个工具，验证 MCP 规范接入（简历关键词）。

## 6. 数据模型（PostgreSQL）

```sql
vehicles(id, name, brand, energy, price_band, status, payload jsonb)
vehicle_configs(id, vehicle_id, code, items jsonb)          -- 简化 BOM
parts(id, name, category, specs jsonb, supplier, compatible jsonb)
knowledge_docs(id, category, title, content, source)        -- policy|review|manual
conversations(id, thread_id, user_id, created_at)
quotes(id, thread_id, vehicle_id, detail jsonb)
orders(id, thread_id, quote_id, status, created_at)
requirement_sheets(id, thread_id, slots jsonb, citations jsonb, status)
config_sheets(id, requirement_id, base_vehicle_id, items jsonb, status)
eval_cases(id, category, input jsonb, expected jsonb)
```

注：M1-M2 在 SQLite 上运行（jsonb 以 JSON 文本存储），建表保持 PostgreSQL 兼容，M4 用 Alembic 管理迁移。

种子数据：`data/vehicles.json`（40 车型起步，含 6 停售、6 未覆盖用于触发定制流；M3 扩至 ≥80）、`data/knowledge/*.md`（政策/口碑/参数各 12 篇起步，M3 扩至各 30）。

## 7. RAG 设计

- 分块：markdown 按标题层级切，chunk 500~800 token，重叠 50
- 检索：结构化过滤（category）+ Chroma 向量 topK=8 →（可选）bge-reranker 精排 → top3
- 引用：chunk metadata `{doc_id, title, source}` 强制随答案返回，前端展示来源角标
- 迁移预留：向量表结构按 pgvector 兼容设计，一行配置切换

## 8. 评测方案

- 评测集 `evals/`（YAML）：slot 抽取 30 例、availability 判定 30 例、recommend 30 例、quote/financing 20 例（纯函数断言）、RAG 20 例
- 运行：`pytest evals/` 自定义 runner；judge 用 LLM-as-judge（1~5 分：对话质量、引用正确性）
- 指标落 `eval_summary`，管理端看板展示；每次真实对话可一键收藏为新评测用例

## 9. 用户端与可选 Android 扩展

主线用户端为单页 Web Chat：SSE 流式渲染、工具调用条与卡片组件、interrupt 操作按钮调 resume API。以下为 Android 扩展（可选）的设计要点：

- OkHttp SSE + kotlinx.serialization 解析事件流；`done` 前断线用 `Last-Event-ID` 续传
- 消息流：文本（Markwon 渲染）/ 工具调用条 / 卡片组件（槽位确认、报价、订单、需求单、配置单）
- interrupt → 渲染操作按钮 → 调 resume API；DataStore 持久化 thread_id 实现会话恢复

## 10. 评审端

M4 主线（极简）：FastAPI + Jinja2 单页——需求单/配置单列表 + 详情 + 通过/驳回/改单，评审动作走 admin API。
可选扩展（Next.js 完整版）：登录 → 知识库管理 → 会话 trace（Langfuse 嵌入）→ 评测看板（指标趋势）。

## 13. 风险与规避

| 风险 | 规避 |
|---|---|
| LangGraph API 迭代快 | requirements 锁定小版本；升级单独提交 |
| 本地 BGE-M3 资源不足（Windows 无 GPU） | 默认 `EMBEDDING_MODE=api` 起步，本地模式主线稳定后再试 |
| 结构化输出偶发不合法 | schema 校验失败自动重试（≤2 次）+ 温度 0 |
| interrupt 状态丢失排查难 | Langfuse trace 节点级打点贯穿两个子图 |
| 评测集冷启动 | M1 起每次真实对话一键沉淀用例 |
| 单人业余时间烂尾 | v1.1 范围裁剪；M1 三周实证校准速度，里程碑滚动修正，可选扩展仅主线完成后启动 |
