#### 意图识别专节（全文唯一的一等公民）

文档给的链路是 **关键词匹配 → 小模型 → 大模型兜底** 三级职责分层；结论是 Qwen3.5-2B（LoRA 后）当默认主力、0.8B 跑端侧/延迟极紧、4B 处理复合意图、9B 没必要（后面已有大模型兜底）。

**为什么这条对你格外重要**：它把「端侧小模型 + 云端大模型协同」讲成了一条可落地的流水线——这正是主计划「六、差异化策略」第 1、2 条想做的东西。别人的项目是「调 API 套壳」，你的是「三级路由 + 置信度门控」，面试叙事完全不同。

**要拿走的是三个不需要微调就能实现的东西**：

1. **三级职责分层**：高频明确意图 → 关键词（零成本、零延迟）；模糊/口语化/复合表达 → 小模型；长尾与争议 → 大模型。三级 badcase 分开统计，迭代时互不干扰。
2. **置信度路由**：让小模型输出 `top-1 意图 + 置信度`（或让它输出「不确定」标签），低于阈值才走大模型兜底。**这是成本结构的核心**，用 Prompt 就能实现。
3. **两步走**：先用 few-shot prompt + 固定意图 schema / JSON 验证链路与阈值，再谈微调。第一步和阶段 1 的「结构化输出 + 校验失败重试」是同一件事。

**与主计划的冲突，先解决掉**：主计划把「模型训练 / 微调 / RL」列为低优先、先跳过。这里的处理是——**读决策层，不动手**。只读到能回答「这一环为什么适合微调」（窄分类任务、能压下兜底调用成本、能把输出格式焊死）与「什么时候不值得微调」（意图体系还在变、样本不足千条），**不学 LoRA 操作**。部署部分同理：只需知道 vLLM / SGLang 能起 OpenAI 兼容 API，让「小模型 → 大模型」两级共用一套 client，不必自己搭。

**落地位置**：`demo/04-dev-assistant`——崩溃日志与需求的意图分类（定位类 / 给修复建议 / 查历史 issue / 需澄清）正好是窄分类任务，且你 3 年 Android / HarmonyOS 经验让这套工具链的可信度最高。

#### 迁移方案专节（我一开始记成 4 阶段，实测是 7 阶段）

完整流程：

1. **双写**：旧表 `t_sign_in_record` 与新分表同时写入
2. **双写一致性校验**：人工抽查 + 写脚本全量比对，不一致的打到日志里排查
3. **刷存量**：写脚本把旧表存量数据导入分表
4. **再校验**：对刷入的存量再做一次一致性比对
5. **切读**：把读旧表的地方全部改成读分表
6. **确认旧表没有新的读请求**：靠 DBA 审计
7. **停止双写**：代码改为只写分表

作者注明整体约**半个月到一个月**，主要耗时在三次一致性校验。

**真正的工程含量在第 5、6、7 步**：切读是灰度、第 6 步是「怎么判断可以停了」、第 7 步才是收尾。多数人只记得「双写 + 迁数据」，答不出后半段——而这后半段才是「不停服迁移」的判据。

**平移成你的场景**（换 embedding 模型 / 换切分策略重建索引）：新旧两套索引双写 → 脚本抽样比对检索结果 → 回填历史文档向量 → 再抽样比对 → 按比例灰度切查询到新索引 → 观察旧索引查询量归零 → 停双写、删旧索引。

这段可以直接背下来，用在「你的 RAG 服务怎么支持不停服重建索引」这类题上。**它是全文少数几处「Java 后端经验能直接变成 AI 工程答案」的地方。**

## 三、五条翻译规则（读 Java 答案时必须做的动作）

直接背 Java 结论，面试官一问「你 Python 里怎么处理」就露馅。每条都要过一遍这个转换：

| Java 说法 | 你要换成的说法 |
| --- | --- |
| 线程池 / `synchronized` / `ReentrantLock` | `asyncio` 事件循环 / 信号量限流 / 不用锁而用单线程事件循环 + 队列 |
| 虚拟线程 pinning | `async` 函数里调了同步阻塞库，整个事件循环被卡住 |
| Full GC / 堆扩容 STW | 进程内存增长 / 容器 OOMKilled / 请求延迟长尾 |
| JVM 参数（如 `-Xms = -Xmx`） | **不学具体参数**，只学「配置项设错会引发稳定性问题」这个思维 |
| `CompletableFuture` 编排 | `asyncio.gather` / `TaskGroup`，注意异常传播与取消 |

**唯一验收**：每个知识点问自己「不这么做会出什么事」。答得出因果，追问就穿不透；只答得出结论，第二层就崩。
