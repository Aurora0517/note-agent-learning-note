# 2026-11-02 W01 Day 4 多轮对话

> 对应 [W01 执行清单](../plans/2026/11/2026-11-02-W01执行清单.md) Day 4：多轮对话。
> 代码：`demo/01-cli-chat/chat.py`（`uv run chat.py`）

## 一句话原理

**大模型 API 是无状态的。** 它不记得你上一句说了什么，所谓「多轮对话」，是客户端每轮都把**完整历史**重新发一遍。

```python
messages.append({"role": "user", "content": 用户输入})
result = stream_turn(...)              # 传的是整个 messages 列表
messages.append({"role": "assistant", "content": result["text"]})   # 回写，下一轮才「记得」
```

第二行 append 是唯一的记忆机制。忘了它，模型就是金鱼。

## 实测三轮（`deepseek-flash`，thinking 关闭，流式）

对话内容：先说「我叫阿伦，在做 Agent 全栈转型，现在学到多轮对话了」，然后追问「我刚才说我叫什么」「那我刚才说自己在学什么」。

| 轮次 | prompt | completion | 缓存命中 | TTFT | 总耗时 | 本轮费用 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 37 | 51 | 0 | 0.65s | 1.04s | ¥0.000513 |
| 2 | 96 | 5 | 0 | 0.61s | 0.74s | ¥0.000247 |
| 3 | 116 | 6 | 0 | 0.70s | 0.85s | ¥0.000298 |
| 合计 | — | — | — | — | — | **¥0.001059** |

**上下文确实生效了**：第 2 轮准确答出「你叫阿伦」，第 3 轮准确答出「你在学多轮对话」。

## 三个观察

### 1. prompt 每轮都在涨，因为它含前面所有内容

```
第 1 轮 prompt = system + 第1轮输入                        = 37
第 2 轮 prompt = system + 第1轮输入 + 第1轮回答 + 第2轮输入  = 96
第 3 轮 prompt = 前面全部 + 第3轮输入                      = 116
```

递推关系是 `prompt(n) = prompt(n-1) + completion(n-1) + 新输入(n)`。

**后果**：n 轮对话的累计输入 token ≈ n²/2 × 平均每轮增量。轮数翻倍，花费变 4 倍。按我这次的增量（约 40 tok/轮）推：

| 轮数 | 累计 prompt tokens（估） | 相对 10 轮 |
| --- | --- | --- |
| 10 | ~2,200 | 1× |
| 20 | ~8,800 | 4× |
| 40 | ~35,000 | 16× |

这就是多轮应用的第一个成本陷阱：**单轮看着便宜，聊久了是平方增长**。也是为什么真实产品必须做上下文管理（滑动窗口、摘要压缩、/clear）。

### 2. 缓存还是没命中——但这次找到了原因和边界

三轮的 `prompt_cache_hit_tokens` 全是 0。怀疑是字段名读错了，专门写了个探针验证：把 system prompt 灌到 980 tokens，同样的前缀连发两次。

```
--- 第 1 次 ---
{"prompt_tokens": 980, "prompt_cache_hit_tokens": 0,   "prompt_cache_miss_tokens": 980, "prompt_tokens_details": {"cached_tokens": 0}}
--- 第 2 次 ---
{"prompt_tokens": 980, "prompt_cache_hit_tokens": 768, "prompt_cache_miss_tokens": 212, "prompt_tokens_details": {"cached_tokens": 768}}
```

结论三条：

- **字段没读错**，`prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens` 都能拿到。
- **缓存是按 64 tokens 粒度做前缀匹配的**：980 的前缀，命中部分正好 768 = 12×64，剩下 212 因为凑不满一个粒度而落空。
- **短前缀（几十到一百多 tokens）干脆不命中**。所以我 96、116 tokens 的对话一次都没蹭上缓存，不是 bug。

**工程含义**：长 system prompt、长文档问答、多轮长历史这类场景，缓存能把输入成本直接砍掉一大半（命中 $0.006 vs 未命中 $0.3，差 50 倍）。但前提是**前缀必须完全一致**——所以 system prompt 要放最前且不能每轮变（别把时间戳、随机数写进去），否则缓存永远不命中。

### 3. TTFT 几乎不随 prompt 增长

0.65s → 0.61s → 0.70s，prompt 从 37 涨到 116 tokens，TTFT 没明显变化。原因和 Day 3 的结论一致：这几百 tokens 的 prefill 在推理成本里可以忽略。**TTFT 真正开始受输入影响，要等 prompt 上到几千 tokens 级别**（长文档、长历史），那时候 prefill 才会变成瓶颈。这一条 Day 3 没条件验证，现在算补上了边界条件。

## 工程细节（都是抄教程容易漏的）

- **失败的那一问要从历史里 pop 掉**。否则 `user` 消息留在列表里但这轮没有 `assistant` 回答，下一轮的上下文里就出现连续两条 user，模型容易答歪，而且白占 token。
- **半途 Ctrl+C 同样要 pop**。流式输出中断时，`result["text"]` 只有半句话，回写进历史就是脏数据。
- **system prompt 放在 messages[0] 且保持固定**，这是缓存前缀能命中的前提。
- **`/clear` 只清 messages、不清统计**，这样累计费用不会因为重开对话就丢——本周硬指标要统计真实调用次数和花费。
- **上下文预算提醒**：prompt 超过 4000 tokens 时打警告。真实产品里这条得做成硬限制或自动摘要，不然用户聊两小时就能烧掉一顿饭钱。
