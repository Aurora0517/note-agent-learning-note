# 2026-11-02 W01 Day 5 健壮性：重试与报错

> 对应 [W01 执行清单](../../plans/2026/11/2026-11-02-W01执行清单.md) Day 5：健壮性。
> 代码：`demo/01-cli-chat/retry.py`（新增）、`main.py` / `chat.py`（接入）、`selftest_retry.py`（自检）

## 一句话原则

**只对「再试一次可能不同」的错误重试。** 其余的立刻停手，并告诉用户该改哪里。

| 错误 | 状态码 | 重试？ | 理由 |
| --- | --- | --- | --- |
| 连接失败 / 超时 | — | ✅ | 网络抖动，第二次可能就好了 |
| 限流 | 429 | ✅ | 等一会儿配额就回来了 |
| 服务端错误 | 5xx | ✅ | 对方的问题，等着就好 |
| key 无效 | 401 | ❌ | 再试一万次也是 401，只烧时间和配额 |
| 无权限 | 403 | ❌ | 同上 |
| 模型不存在 | 404 | ❌ | 名字写错了，重试改不了拼写 |
| 参数错误 | 400 | ❌ | 代码 bug，重试没意义 |

## 实现拆成四块（`retry.py`）

| 函数 | 职责 |
| --- | --- |
| `retryable(exc)` | 判定表：这个异常值不值得重试 |
| `backoff_delay(attempt)` | 指数退避 1s → 2s → 4s… 封顶 16s，带 ±20% 抖动 |
| `retry_after(exc)` | 服务端给了 `Retry-After` 头就听服务端的 |
| `call_with_retry(fn, max_attempts=3)` | 串起来执行，只对可重试错误退避 |
| `describe(exc)` | 把异常翻译成「是什么 + 该怎么办」 |

## 验证证据：五个故障场景全跑了一遍

### 1. 429 两次后成功（自建假服务端，零成本）

```
$ uv run main.py --no-stream --retries 3 "测试重试"
超时：30s　最多尝试：3 次

  [重试 1/2] 429，1.0s 后重试…
  [重试 2/2] 429，1.0s 后重试…
这是假服务端的回答，说明重试成功了。
总耗时：4.073s
```

服务端日志确认收到 **3 次**请求。两次退避都是 1.0s 而不是 1s→2s，因为假服务端返回了 `Retry-After: 1`，**服务端的指示优先于本地退避算法**——它比我们清楚什么时候能再来。

### 2. 一直 429，重试 2 次后放弃

```
  [重试 1/1] 429，1.0s 后重试…

调用失败。
被限流了（429）。
  → 说明请求太密或余额不足。降并发、放慢发送节奏，或者确认账户还有余额。
```

### 3. 真实 401（key 填错）

```
调用失败。
API key 无效或已过期（401）。
  → 检查 .env 里的 OPENAI_API_KEY：有没有多余空格、引号，或者 key 是不是被平台回收了。
```

**没有重试**，立即返回。这是判定表生效的直接证据。

### 4. 端点连不上（连接被拒）

```
  [重试 1/1] APIConnectionError，1.0s 后重试…

调用失败。
连不上服务器。
  → 检查网络/代理是否通，OPENAI_BASE_URL 是否写对（本地探测可用 curl 直接试一下）。
```

### 5. 超时（服务端睡 5s，客户端 1s 超时）

```
  [重试 1/1] APITimeoutError，1.2s 后重试…

调用失败。
请求超时。
  → 网络慢或服务端排队。可以调大超时时间（--timeout），或者换低峰时段跑。
```

### 6. 决策表自检（`uv run selftest_retry.py`，离线、免费）

```
✅ 500 / 503 / 429 / 超时 / 连不上  → 重试
✅ 400 / 401 / 403 / 404           → 不重试
退避序列（base=1s, cap=16s）：1.0s, 2.1s, 4.7s, 7.4s, 15.1s, 16.0s
全部通过
```

留这个脚本的原因是：重试写错的两个方向都很贵——该重试的不重试，一次网络抖动就报错；不该重试的乱重试，401 被重放 N 次，白烧配额还刷满日志。改 `retry.py` 后跑一遍，防止手滑。

## 五个关键设计决策（这些才是 Day 5 的真收获）

**1. 关掉 SDK 自带的重试。**
OpenAI SDK 默认 `max_retries=2`，叠加上自己的 3 次，一次调用最坏是 **3×3 = 9 个真实请求**。日志上看不出来，账单上全是。所以 `OpenAI(..., max_retries=0)`，重试权收归自己，每次重试都打日志。

**2. `max_attempts` 是「总尝试次数」，不是「重试次数」。**
`max_attempts=3` 意味着最多发 3 次请求（首发 + 2 次重试）。这个语义必须写进注释——「重试 3 次」到底发 3 个还是 4 个请求，是团队协作里最常见的理解分歧。

**3. 流式只重试「建立连接」，不重试已经吐字的流。**
`create(stream=True)` 拿到响应头就算建连成功，此时重试是安全的；一旦开始吐字就不能重来，否则用户屏幕上的半句话没法撤回，会看到同一段内容讲两遍。中途断流的处理是**保留已输出内容 + 明确告知不完整**：

```
[输出中断] 已收到 12 段，这句回答不完整。
```

**4. 超时要自己设，而且要比直觉短。**
SDK 默认 600s——用户会盯着一个卡死的界面十分钟。这里设 30s（`--timeout` 可调）。**失败得快**比**卡住不动**体验好得多，尤其在 Agent 场景里，超时是常态不是异常。

**5. 报错只给人话，堆栈藏在 `DEBUG=1` 后面。**
默认输出是「是什么 + 下一步做什么」，不给用户看 traceback。需要排查时 `DEBUG=1 uv run main.py` 拿完整堆栈。这个开关成本极低，但省掉的「贴一屏堆栈问同事」的沟通成本很高。

## 踩到的四个坑

1. **openai 3.x 用的是 `httpx2`，不是 `httpx`。** 自检脚本 `import httpx` 直接 ModuleNotFoundError。这个坑很隐蔽：教程里全是 `httpx`，而你的环境里根本没有这个包。
2. **抖动把上限顶破了。** 第一版 `min(cap, base*2^n)` 先夹上限再加抖动，结果退避序列里出现了 **19.0s > 16s**。正确写法是 `min(cap, base*2^n * jitter)`——先抖动再夹。
3. **`os.environ.setdefault` 让 `--timeout` 失效。** setdefault 在环境变量已存在时不会覆盖，导致命令行参数被 `.env` 里的 `OPENAI_TIMEOUT` 抢先。改成显式赋值，优先级命令行 > 环境变量 > 默认。
4. **`chat.py` 全失败时总结文案是错的。** 一轮都没成功时打出「这轮什么都没问」，语义相反。改成「本次没有成功的对话轮次」。
